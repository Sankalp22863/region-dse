Getting it runningCode & Setup

The environment, the toolchain, and the exact commands that take a C kernel to a validated region of buildable designs.

Sankalp22863/DSEPruning Private repo · access required Open on GitHub

The repository implements the search described in the post: a design space defined by tile, unroll and pipeline-II knobs; a region abstraction that splits, prunes and promotes boxes in that space; a cheap analytical evaluator to shape the bounds; and real Vitis HLS synthesis to ground the answer. It ships ten PolyBench kernels, cached synthesis results, and the scripts that regenerate the paper's metrics.

Everything below was read off the repository itself rather than transcribed from its README — where the two disagree, the code wins and the difference is noted in Caveats.

02

Install

  1. Clone

    Clone plainly. A recursive clone aborts on an unmapped gitlink, and you do not need the submodules for the synthetic path — the toolchain scripts fetch their own sources anyway.

    shell
    git clone git@github.com:Sankalp22863/DSEPruning.git
cd DSEPruning

    If you do want them, name the paths explicitly:

    shell · path-limited, works
    git submodule update --init --recursive \
    deps/llvm-project deps/GNN-DSE dse_tools/ScaleHLS-HIDA dse_tools/AutoDSE

  2. Create the environment

    Creates a conda environment called dsepruning on Python 3.10 and installs the four packages. Safe to re-run — it skips creation when the environment exists, and re-sources the toolchain env files each time.

    shell · from the repo root
    source env_setup.sh
pip install pymoo          # only if you will run the NSGA-II stage

    In any later shell:

    shell
    eval "$(conda shell.bash hook)"
conda activate dsepruning

  3. Build the HLS toolchain — optional, hours

    Needed only for the ScaleHLS evaluators and for applying a chosen point to MLIR. It builds ScaleHLS-HIDA, MLIR 18.1.8 and prose-opt in dependency order into one prefix, defaulting to dse_tools/ inside the repo. Run it before sourcing env_setup.sh, then source that again so the regenerated environment files are picked up.

    shell
    bash setup/setup_all.sh --prefix dse_tools --jobs 16
# --full forces a clean rebuild of every component

    These are build scripts, not activation scripts — run them with bash, never source. setup_scale_hls.sh installs system packages with sudo as its first action, so read it before running on a machine you share.

  4. Point at Vitis HLS — optional

    This one is source-only: it exports XILINX_HLS and puts vitis_hls on your PATH. The path inside it is site-specific, so set VITIS_HLS_ROOT to your own 2022.1 install first.

    shell
    source setup/setup_vitis_hls.sh
03

Run a search

Run everything from the repo root — the entry points put src/ on sys.path themselves, so there is no PYTHONPATH to export.

Start here. The synthetic evaluator needs no toolchain and finishes in about a second, spending 30 evaluations over a space of roughly two million points. Pass a seed if you want the run back:

shell · synthetic, no toolchain
python src/dse_run/run_prose.py
python src/dse_run/run_prose.py --seed 1          # otherwise a fresh seed per run

It writes roi_regions.json — the regions, the pruned percentage and the seed — into the working directory, alongside the sampled Pareto points as CSV and the Pareto-front, region-evolution and Pareto-growth plots. Add --contracts --plots for the contract exports and the density-heatmap and quality-ranking figures.

Then give it a real kernel. Derive the knob space from the C source; the JSON lands next to it:

shell · design space
python src/design_space/extract_design_space.py benchmark/polybench/gemm/gemm.c

Five kernels ship with a design space already committed — gemm, 2mm, 3mm, atax and bicg. Those are the ones the non-synthetic evaluators can run today; the other --kernel choices stop with Design space not found.

With synthesis in the loop. Source the Vitis environment first. Results are cached under the kernel's <kernel>_vitis_cache/ directory and re-used, and for every non-synthetic evaluator the outputs are redirected to benchmark/polybench/<kernel>/Results/:

shell · measured
source setup/setup_vitis_hls.sh
python src/dse_run/run_prose.py --evaluator hls --kernel gemm --budget 30

The full pipeline — the cheap analytical model shaping the bounds, real synthesis grounding the answer, contracts exported:

shell · the deliverable
python src/dse_run/run_prose.py \
    --evaluator mixed-scalehls --mixed-split 0.6 \
    --kernel gemm --budget 30 --batch-size 48 \
    --contracts --plots

Refine inside the region to pick a single point. This stage needs pymoo, and despite the flag name its synthetic evaluator calls the real ScaleHLS binaries; it also re-checks the final front with Vitis unless you pass --no-verify:

shell · NSGA-II inside the ROI
python src/genetic_algorithm/lsga_pareto.py --evaluator synthetic --kernel 2mm \
    --roi-json benchmark/polybench/2mm/Results/2mm_roi_regions.json \
    --num-workers 40

Multi-kernel pipelines. The hierarchical flow partitions the device budget across stages before searching, so any combination of survivors is jointly feasible. It runs end to end with no toolchain:

shell · hierarchical
python src/prose_hier/run_prose_hier.py --benchmark two_stage_mm \
    --evaluator synthetic --stage1-budget 200 --stage2-budget 80 \
    --contracts --plots

06

Reproducing the results

The two hierarchical experiments run with no toolchain at all — the quickest way to watch the method's claims land:

shell
# baselines on equal budget: monolithic, random, comm-oblivious, comm-aware
python Paper_Experiments/hier_experiment.py --benchmark two_stage_mm --seeds 5 --plots

# the Pareto shift on an mma to conv pipeline, plus ROI containment
python Paper_Experiments/mma_conv_shift_experiment.py --benchmark mma_conv --seeds 3 --plots

# summary bar chart across whatever searches you have run
python src/results/plot_pruning_summary.py

Each writes its JSON and figures under the benchmark's own Results/hier/experiment/ directory. Add --vitis-points N or --pnr to put real synthesis and place-and-route behind the comparison.

Retention is the metric to read: Pareto retention is the share of globally Pareto-optimal designs still inside the retained regions, and hypervolume retention asks the same of the dominated area, against a reference point at 1.05× the worst Pareto latency and area. Both need the full sweep --exhaustive performs, so compute them on a small space — the default synthetic space is far too large for that pass to finish.

07

Caveats

Things that will otherwise cost you an afternoon:

  • The repo is private. The link above returns a 404 without access, and HTTPS cloning will prompt for credentials. Clone over SSH with a key on the account.
  • Do not clone recursively. git submodule update --init --recursive aborts immediately on a gitlink that has no entry in .gitmodules. Name the four submodule paths explicitly, as in step 1, or skip them — the setup scripts fetch what they need.
  • The committed toolchain env files ship pre-filled. The source_*_env.sh files carry absolute paths from the machine they were generated on, and env_setup.sh sources them and reports success even when those directories do not exist. Running the setup scripts regenerates them correctly.
  • Check the part before you trust a feasibility result. The default is xczu7ev-ffvc1156-2-e with --dsp-budget 1382, while the README describes an Alveo U250 throughout. Pass --part and --dsp-budget together, explicitly.
  • The synthetic evaluator ignores --kernel. Its knob space is hardcoded and unrelated to the real design spaces, and its latency error against synthesis is large. Use it to watch the algorithm behave, not for QoR numbers.
  • Measured runs are slow, and that is the point. Each HLS evaluation is a synthesis invocation; place-and-route is 30–90 minutes per point. Keep --budget low and let the JSON cache do its job — deleting it means paying for all of it again.
  • The toolchain build is a project of its own. It compiles MLIR 18.1.8 from source, needs python3.11 alongside the 3.10 environment, and installs system packages with sudo. Give it a real machine and --jobs.
  • The README is stale in places. Where this page and the README disagree — environment name, dependency list, default part, kernel list, cache paths, the Python floor — this page follows the code.

Numbers, tables and the algorithm write-up land in the post once the paper clears review.
